# دليل التشغيل والصيانة (Runbook)

> لفريق التشغيل. الأوامر تُنفذ من مجلد `deploy/` على الخادم.

## 1. المراقبة

| ما يُراقب | كيف | الحد |
|---|---|---|
| حياة الـ API | `GET https://<API_DOMAIN>/health` | 200 |
| الجاهزية | `GET /ready` (قاعدة البيانات، الترحيلات، التخزين) | 200؛ 503 = لا تُوجَّه حركة |
| حالة الحاويات | `docker compose ps` | كلها `healthy`/`running` |
| العامل | `docker compose logs worker --since 1h` | سطور JSON لكل مهمة؛ أي `error` يُفحص |
| الإشعارات الفاشلة | لوحة الإدارة ← الإشعارات (سجل الإرسال) | لا تراكم للحالة «فاشلة» |
| فحوص الاتساق المالي | لوحة الإدارة ← المطابقة ← فحوص الاتساق | صفر مشكلات |
| المساحة | `df -h`، حجم `backups/` | أقل من 80% |
| الشهادات | يجددها Caddy تلقائيًا؛ `docker compose logs caddy` | — |

اربط `/health` و`/ready` بأداة مراقبة خارجية (مثل UptimeRobot أو أداة مزود الاستضافة) مع تنبيه.

## 2. النسخ الاحتياطي

- **يدويًا / قبل أي تحديث**: `docker compose run --rm backup` ← مجلد في `deploy/backups/<التاريخ>` فيه `db.dump` و`storage.tar.gz` و`manifest.json` (بصمات SHA-256، عدد صفوف كل جدول، مجاميع الدفتر، فهرس الملفات، نتائج فحوص الاتساق). يحتفظ بأحدث `BACKUP_KEEP` نسخة.
- **مجدولًا** (cron على الخادم، يوميًا 02:10):
  ```cron
  10 2 * * * cd /srv/events/deploy && docker compose run --rm backup >> backups/backup.log 2>&1
  ```
- **خارج الخادم**: انسخ `backups/` يوميًا إلى تخزين خارجي مشفّر (مثل `rclone sync backups remote:events-backups`). نسخة على نفس الخادم ليست نسخة احتياطية.
- **المطابقة التامة** تتطلب لحظة هادئة (الليل)، لأن البصمة تُؤخذ قبل التفريغ. مع قاعدة مُدارة فعّل PITR أيضًا.

## 3. الاستعادة

لا تُستعاد أبدًا فوق بيانات عاملة: الأداة ترفض أي قاعدة أو تخزين غير فارغ، وتتحقق من البصمات قبل أن تكتب شيئًا.

**استعادة بعد كارثة** (خادم جديد أو فقدان البيانات) — مُختبرة في `smoke-test.sh`:

```bash
# على الخادم الجديد: نفس .env و secrets.env، ومجلد backups/ منسوخ من التخزين الخارجي
docker compose up -d postgres                       # قاعدة فارغة
docker compose run --rm restore /data/backups/<النسخة> \
  "postgres://<POSTGRES_USER>:<POSTGRES_PASSWORD>@postgres:5432/<POSTGRES_DB>" /data/storage
docker compose up -d                                 # migrate يتأكد من المخطط ثم يبدأ كل شيء
```

مع `STORAGE_DRIVER=s3` اجعل الوجهة الأخيرة `s3` بدل `/data/storage` (حاوية أو بادئة فارغة مضبوطة في `S3_*`).

**تمرين استعادة** (شهريًا، دون لمس البيانات العاملة):

```bash
docker compose exec postgres createdb -U <POSTGRES_USER> events_drill
docker compose run --rm restore /data/backups/<النسخة> \
  "postgres://<POSTGRES_USER>:<POSTGRES_PASSWORD>@postgres:5432/events_drill" /data/restore-drill
docker compose exec postgres dropdb -U <POSTGRES_USER> events_drill && docker volume rm events_restore_drill
```

تنجح الاستعادة فقط إذا تطابقت البصمات، وعدد صفوف كل جدول، ومجاميع الدفتر، وفهرس الملفات، ونتائج فحوص الاتساق مع المصدر. أي مشكلة كانت موجودة في المصدر تُنقل كما هي ويُبلَّغ عنها كتحذير. سجّل في كل تمرين وقت الاستعادة الفعلي (RTO) وعمر آخر نسخة (RPO).

## 4. حوادث شائعة

| الحالة | الإجراء |
|---|---|
| بوابة الدفع متوقفة | عطّل طريقة الدفع مؤقتًا من «طرق ومزودو الدفع» (الحجوزات المؤقتة تنتهي وتُحرَّر تلقائيًا). بعد العودة، الإشعارات المتأخرة تُعالج: إن كان الموعد ما زال متاحًا يُؤكَّد، وإلا يُعلَّم للاسترداد. |
| إشعارات الويب هوك تُرفض | سجل أحداث الدفع في صفحة «طرق ومزودو الدفع» بلوحة الإدارة يعرض سبب الرفض (توقيع، مبلغ). تحقق من تطابق السر في `secrets.env` مع لوحة المزود. لا تُعدَّل الدفعات يدويًا. |
| مشكلة في فحوص الاتساق | لا تعدّل قاعدة البيانات مباشرة (القيود محمية من التعديل والحذف). افتح المطابقة وحدد العملية الناقصة؛ التصحيح يكون بقيد عكسي عبر الإجراءات المالية المعتمدة. |
| تسرّب سر | **سر دفع**: أنشئ سرًا جديدًا لدى المزود، حدّث `secrets.env`، ثم `docker compose up -d api worker`. **`JWT_SECRET`**: غيّره وأعد التشغيل، فتنتهي كل الجلسات فورًا ويسجل الجميع الدخول من جديد. **كلمة مرور قاعدة البيانات**: `ALTER USER` ثم تحديث `.env`. سجّل الحادثة. |
| حساب موظف مخترق | من «المستخدمون»: إيقاف الحساب، فيُمنع الوصول وتُلغى جلساته فورًا. راجع سجل التدقيق لنفس الفاعل. |
| امتلاء القرص | قلّل `BACKUP_KEEP` بعد التأكد من وجود النسخ خارج الخادم، و`docker system prune` للصور القديمة. |
| خدمة لا تبدأ | `docker compose logs <service>`: رسائل الإعداد صريحة (مثل «JWT_SECRET: use a random value»). `migrate` الفاشل يمنع بدء `api` عمدًا. |

## 5. الصيانة الدورية

- **أسبوعيًا**: مراجعة فحوص الاتساق، والإشعارات الفاشلة، وطلبات الاسترداد والتسويات المعلقة، والنزاعات المتجاوزة للمهلة.
- **شهريًا**: تمرين استعادة؛ مطابقة كشوف البوابة والبنك (المطابقة ← تشغيل جديد)؛ مراجعة أدوار الموظفين وحذف غير المستخدمين؛ `npm audit` على المستودع وتحديث الصور (`docker compose pull` لـ postgres/caddy).
- **أسعار الصرف**: تُدخل بتاريخها ومصدرها قبل إصدار تقارير متعددة العملات؛ التقارير لا تحوّل دون سعر موثق.
- **سنويًا**: تدوير `JWT_SECRET` وأسرار التكاملات؛ اختبار اختراق مستقل.

## 6. السجلات والخصوصية

- سجلات الحاويات بصيغة JSON، وترويسة `authorization` محجوبة منها. رموز التحقق لمرة واحدة لا تُحفظ بعد الإرسال.
- سجل التدقيق داخل التطبيق غير قابل للتعديل أو الحذف على مستوى قاعدة البيانات، ويُحجب منه أي سر.
- لتحديد مدة الاحتفاظ بالسجلات استخدم إعدادات Docker (`log-opts: max-size/max-file`) أو مجمّع سجلات.
